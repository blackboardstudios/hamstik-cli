# Release signing, integrity, and provenance design (CLI-28)

Authoritative for how Hamstik CLI release artifacts prove integrity and
authenticity. Companion to [RELEASE.md](RELEASE.md) (build pipeline) and
[VERSIONING.md](VERSIONING.md). Implements SPEC §72 (verify downloads via
published checksums) and §74 (release security). Status markers below
distinguish what is implemented today from what awaits provisioning.

## Threat model

What we defend against, in the public GitHub-hosted release model:

1. **Tampered or corrupted download** — a modified archive (mirror
   compromise, truncation, corrupted transfer) presented as an official
   release. Defended by per-artifact sha256 checksums plus aggregate
   `sha256.sum`, and by Sigstore-signed attestations binding exact
   digests to this repository's build.
2. **Wrong-build substitution** — an archive that is valid but was not
   built by the official pipeline (e.g. attacker-uploaded asset on an
   unguarded release). Defended by provenance attestations: a subject
   digest without a matching attestation from `blackboardstudios/hamstik-cli`
   CI is not a valid release artifact, and verification is exercised
   automatically in the release pipeline.
3. **Version confusion / mismatch** — an artifact claiming to be `vX`
   that is not the tagged source. Defended by the release gate
   (tag/version/changelog consistency, CLI-27) and by the embedded
   commit in `hamstik version` matching the tag.
4. **Dependency-level compromise** — a malicious or vulnerable crate in
   the shipped binary. Defended by locked `Cargo.lock`, `cargo-deny`
   advisories/licenses in CI (observed blocking: RUSTSEC-2026-0285), and
   a CycloneDX SBOM published per release so downstream consumers can
   audit the exact component set.

Out of scope / residual risks, documented deliberately:

- **Compromised runner or workflow** — mitigated by least-privilege
  permissions, SHA-pinned actions, no secrets in the release path
  (RELEASE.md §Security posture). A fully compromised runner can build
  malicious artifacts; attestations would then attest malicious builds.
  This residual risk is inherent to CI-hosted builds; platform code
  signing does not eliminate it either, it only changes who must be
  compromised (key holder vs runner). Mitigations beyond CI hardening
  (e.g. reproducible-build verification builds) are tracked as future
  work under CLI-30/lifecycle.
- **Sigstore availability** — verification via `gh attestation verify`
  needs GitHub's attestation API and the Sigstore bundle embedded in the
  response; offline verification is possible from the bundle file.

## Decision 1 — artifact integrity: sha256 checksums (shipped)

Every downloadable artifact carries a published `sha256` sidecar
(`hamstik-cli-<target>.tar.gz.sha256` …) plus an aggregate `sha256.sum`,
generated by cargo-dist. Users verify with `sha256sum -c sha256.sum`.
The release pipeline itself re-verifies checksums against the fetched
artifacts in the `host` job **before** the release is published — a
checksum mismatch fails the workflow (fail closed).

## Decision 2 — build provenance: GitHub artifact attestations (shipped)

Chosen mechanism: **`actions/attest-build-provenance`** (GitHub's
Sigstore-backed attestation, in-toto / SLSA build-provenance predicate).
Rationale:

- No long-lived keys to custody: signing uses a short-lived Sigstore
  certificate issued to the workflow's OIDC identity. This satisfies
  "prefer modern, maintainable mechanisms" and "credentials remain in
  secure CI/platform secret storage" without introducing any key
  management burden.
- First-party GitHub integration: attests the exact files uploaded to
  the release; verification is `gh attestation verify` — a one-command
  user experience on machines that have `gh` (or the REST API for others).
- Native fit with the cargo-dist/GitHub Actions release architecture;
  no third-party service dependency beyond GitHub/Sigstore public good
  instance (the repository is public).

What is attested: every downloadable release asset — the five platform
archives, `source.tar.gz`, and the CycloneDX SBOMs — bound to the
SLSA v1.0 provenance of the exact workflow run that built them
(commit, workflow ref, runner).

## Decision 3 — platform code signing (deferred; provisioning required)

Windows (Authenticode) and macOS (Developer ID + notarization) signing
require purchased certificates and organizational identity decisions
(CA choice, certificate custody, notarization profile). Until those
credentials exist and are configured as CI secrets, artifacts carry no
platform signature; the OS Gatekeeper/SmartScreen path is served by the
documented verification procedure instead. **This is the one open
provisioning decision** — see "Provisioning checklist" below.

## Decision 4 — artifact signing (Sigstore bundles, shipped)

Individual artifact signatures beyond build provenance (e.g.
`minisign`/`sigstore` detached signatures per archive) are **not**
added: the Sigstore attestation bundle already provides a verifiable
signature binding each artifact digest to the official build identity,
and duplicating that with a separate key-based scheme would add a
second custody burden without closing a gap in the threat model above.
If a future requirement (e.g. air-gapped verifiers without `gh`)
demands offline key-based signatures, revisit as a documented decision.

## Verification procedure (users)

```bash
# 1. Integrity — checksums
sha256sum -c sha256.sum

# 2. Authenticity — provenance (requires gh CLI ≥ 2.57)
gh attestation verify hamstik-cli-x86_64-unknown-linux-gnu.tar.gz \
  --repo blackboardstudios/hamstik-cli

# 3. Identity — the binary reports its exact build
./hamstik-cli-x86_64-unknown-linux-gnu/hamstik version
```

A download is trustworthy when all three hold: checksum matches the
published aggregate, attestation verifies against this repository, and
the reported version/commit match the release tag. `gh attestation
verify` fails closed on missing, tampered, or foreign attestations.

## Fail-closed enforcement in the release pipeline

The `host` job, **before** publishing:

1. verifies every fetched artifact against the published `sha256.sum`;
2. generates build-provenance attestations for every downloadable asset
   (archives + source tarball + SBOMs);
3. verifies the attestations locally against the returned bundle;
4. only then runs `dist host --steps=upload --steps=release`.

A checksum mismatch, attestation failure, or verification failure fails
the workflow and the release is never published.

## SBOM (shipped)

CycloneDX 1.5 JSON SBOMs are generated from the committed `Cargo.lock`
by `cargo-cyclonedx` (version-pinned in the workflow) for the two
released-in-lockstep crates (`hamstik-cli`, `hamstik-api-client`) and
attached to each release as `hamstik-cli.cdx.json` /
`hamstik-api-client.cdx.json`. The SBOM reflects the dependency set that
produced the release binaries (release profile, default features).

## Signing design — decision record

| Aspect | Decision |
| --- | --- |
| Integrity | sha256 per artifact + aggregate, verified pre-publish |
| Authenticity | Sigstore build-provenance attestations via GitHub Actions OIDC |
| Key custody | none (short-lived Sigstore certificates; no keys to rotate) |
| Key rotation | n/a — ephemeral certificates; repository OIDC trust is the anchor |
| Platform signing | deferred until Authenticode/Apple credentials are provisioned (below) |
| Offline verification | checksums: yes; attestations: via `gh attestation verify --bundle` from a saved bundle |
| Failure behavior | fail closed before release publication |

## Provisioning checklist (requires repository owner)

1. Purchase/configure an Authenticode code-signing certificate and an
   Apple Developer ID certificate; store in CI secrets or a hardware
   token service. (Windows: SPEC §68 signing; macOS: SPEC §69 signing +
   notarization.)
2. Revisit this document's Decision 3 and extend the release workflow
   with `windows-sign`/`notarize` steps and verification checks.
3. Update the verification procedure with the platform-specific checks.

Until provisioned, the signing-verification acceptance criterion is met
by the Sigstore attestation mechanism; platform-signing criteria remain
open and CLI-28 stays honest about that in its tracker state.

## Security invariants

- No signing secret exists in the repository or workflow; OIDC-based
  short-lived credentials only.
- No credential material appears in attestations (they contain build
  provenance: repo, ref, commit, workflow path — never secrets).
- Verification never sends credentials (public attestation API).
