# Installation design (CLI-29)

Authoritative for how users install released Hamstik CLI binaries.
Companion to [RELEASE.md](RELEASE.md) (build pipeline) and
[SIGNING.md](SIGNING.md) (verification). Implements SPEC §68 (Windows),
§69 (macOS), §70 (Linux), §72 (direct download). Decisions recorded in
the decision record below are binding; "deferred" items state what is
intentionally absent and why.

## Decision record

| Channel | Decision | Status |
| --- | --- | --- |
| Direct download (all platforms) | GitHub Release archives + `install.sh` / PowerShell installers | shipped |
| macOS | Homebrew tap `blackboardstudios/homebrew-hamstik`, formula auto-published per release | shipped (first publish on next release run) |
| Windows | GitHub Release direct download, PowerShell installer; **Winget via generated manifests + documented manual PR** to `microsoft/winget-pkgs` | shipped (Winget PR per release) |
| Linux | **Tarball + shell installer**; `.deb`/`.rpm` and hosted APT/RPM repos deliberately deferred | shipped |
| npm wrapper (`@hamstik/cli`) | deferred (SPEC §71 optional) | deferred |

## Quick install (per channel)

### macOS — Homebrew (SPEC §69)

```bash
brew tap blackboardstudios/hamstik https://github.com/blackboardstudios/homebrew-hamstik
brew install blackboardstudios/hamstik/hamstik
```

- Both supported architectures (Intel, Apple Silicon) resolve
  automatically from the formula's per-target blocks.
- Upgrades: `brew update && brew upgrade blackboardstudios/hamstik/hamstik`
  (the release pipeline commits an updated formula per stable release;
  prereleases are not tapped).
- Uninstall: `brew uninstall blackboardstudios/hamstik/hamstik`.

### Windows — PowerShell installer or direct download (SPEC §68)

```powershell
# PowerShell installer (fetches and installs the right archive)
irm https://github.com/blackboardstudios/hamstik-cli/releases/latest/download/hamstik-cli-installer.ps1 | iex
```

The installer downloads the matching `hamstik-cli-x86_64-pc-windows-msvc.zip`
and installs `hamstik.exe` for the current user. Direct download remains
the always-available fallback (SPEC §72).

- Winget: manifests are generated into `winget/` per release and
  submitted as PRs to `microsoft/winget-pkgs` by a maintainer (deliberate
  manual step, documented below). Once accepted,
  `winget install BlackboardStudios.HamstikCLI` works.
- Upgrade: re-run the installer for the new release (it replaces the
  installed binary), or `winget upgrade` once the manifest path is live.
- Uninstall: delete the installed binary directory (documented in
  `hamstik-cli-installer.ps1` output).

### Linux — shell installer or tarball (SPEC §70)

```bash
curl --proto '=https' --tlsv1.2 -LsSf \
  https://github.com/blackboardstudios/hamstik-cli/releases/latest/download/hamstik-cli-installer.sh \
  | sh
```

- Installs into `~/.hamstik/bin` and prints PATH guidance. The installer
  fetches the matching archive (`x86_64-unknown-linux-gnu` or
  `aarch64-unknown-linux-gnu`) for the running machine; glibc ≥ 2.35 is
  the runtime baseline (design/RELEASE.md §matrix).
- Direct download fallback: fetch
  `hamstik-cli-<target>.tar.gz`, verify with `sha256sum -c sha256.sum`
  (design/SIGNING.md), unpack, add to `PATH`.
- Upgrade: re-run the installer (or download the new tarball and replace
  the binary).
- Uninstall: remove the installed binary directory.
- **Deliberate exclusions**: no `.deb`/`.rpm`/APT/RPM hosting yet. SPEC
  §70 lists them as "initial" candidates, but CLI-29's scope guidance is
  the smallest maintainable set; hosted repositories are explicitly
  "optional post-launch enhancements". Revisit when user demand or a
  package-repository partner appears.

## How the pipeline maintains the channels

- **Installers** (`hamstik-cli-installer.sh`, `...-installer.ps1`) are
  generated by cargo-dist per release (`installers = ["shell",
  "powershell", "homebrew"]` in `dist-workspace.toml`) and attached to
  the release automatically. They carry no credentials and no
  environment-specific configuration: they fetch from the public release
  URL for the version they were generated for.
- **Homebrew formula** (`hamstik.rb`) is generated per release and
  committed to `blackboardstudios/homebrew-hamstik` by the
  `publish-homebrew-formula` job. The formula references the release's
  archives by absolute URL + sha256. Prereleases are not tapped.
- **Winget manifests** are generated into `winget/` per release and
  committed to this repository (a maintainer then opens the
  `microsoft/winget-pkgs` PR — see below).
- **SBOM/attestations** cover all downloadable assets including
  installers (design/SIGNING.md).

## Homebrew tap token (provisioning note)

Cross-repo pushes are outside the default `GITHUB_TOKEN`'s scope, so the
`publish-homebrew-formula` job checks out the tap with
`secrets.HOMEBREW_TAP_TOKEN` — a **fine-grained PAT with Contents:write
on `blackboardstudios/homebrew-hamstik` only**, nothing else. If the
secret is absent the job fails with an authentication error; create it
under repository Settings → Secrets → Actions. The token is rotated by
its owner; no other repository should be in its scope.

## Winget: sustainable workflow (deliberate manual step)

Winget publishing has no cargo-dist integration and no first-party
GitHub Actions publisher. The chosen sustainable path:

1. Each stable release generates versioned manifests
   (`winget/BlackboardStudios.HamstikCLI/<version>/...yaml` — installer,
   locale, version) committed to this repository, with installer URLs and
   sha256 pointing at the GitHub release.
2. A maintainer copies the new version directory into a fork of
   `microsoft/winget-pkgs` and opens a PR there (the standard community
   flow, same as thousands of other CLIs). Manual PRs per release are a
   deliberate, documented choice (CLI-29 scope allows this).
3. Once merged, `winget install BlackboardStudios.HamstikCLI` and
   `winget upgrade` work; manifests in this repository remain the
   staging copy and audit trail.

The manifests embed no credentials, only public release URLs and
checksums.

## Post-install smoke test (all channels)

After installing, verify:

```bash
hamstik --help          # starts
hamstik version         # reports the expected release
hamstik doctor --local-only   # offline diagnostic passes
```

This is the same smoke suite the release pipeline runs against every
artifact before publishing it (CLI-27).

## Security invariants

- Installers and manifests fetch only from public GitHub Release URLs;
  no telemetry, no credential material, no environment-specific
  configuration (AC-checked).
- The shell/PowerShell installers live in the release/distribution
  layer only — no installer logic exists in the product binary.
- Verify downloads per design/SIGNING.md before use.
